## 1. Core domain principles

- **[CONFIRMED]** ULTM8 is a multi-tenant SaaS platform for martial-arts school management. (§1.3)
- **[OBSERVED IN DESIGNS]** The sample data brands the product "ULTM8," built by "IMAS – Innovative Martial Arts Systems." Treat this as illustrative Figma sample content, not a confirmed legal/business name to hard-code anywhere.
- **[CONFIRMED]** The tenant unit is the **School** (optionally grouped under a **Franchise**). End users are **Students**, some of whom are managed by a **Guardian** (§14 below). Staff-side customer-facing roles are School Owner/Manager, Branch Staff, Franchise Owner, and **Instructor** — Instructor now has its own genuine login, not merely records School staff manage (§3, §8.2, confirmed Pass 2). **Platform Admin** staff are a deliberately separate identity, never a tenant-side role. (§4.4, §6.1, §8.2)
- **[CONFIRMED]** Five domain concepts anchor the whole product: belt/rank progression per discipline, class scheduling against a weekly recurring timetable, membership sales (Subscription / Class Pack / Weekly Pass / Friend Pass / Trial — five types, expanded from the original three, §6 below), liability waivers with e-signature, and QR-code class check-in — all delivered through a multi-language (**4** languages — English (UK), Portuguese (BR), Spanish, Arabic — including Arabic/RTL) and multi-currency (6 currencies) experience administered via a CMS-style translation tool. (§1.3, §6.1, §11.1)

## 2. Organisation hierarchy

- **[CONFIRMED]** Hierarchy is **Franchise → School → Branch**. (§1.2, §6.2)
- **[CONFIRMED]** A Franchise MAY own many Schools. (§6.2)
- **[CONFIRMED]** A School's link to a Franchise is **optional (nullable)** — an independent, non-franchised School is a first-class case, not an edge case. (§1.2, §6.2)
- **[CONFIRMED]** A School MAY have many Branches. (§6.2)
- **[CONFIRMED]** Branch's field set mirrors School's — name, address, contact phone, timezone, currency override, branding — beyond the already-confirmed `id`/`school_id` and its RLS-enforced role as an access boundary for `TimetableSlot`, `Class`, `Instructor`, and `Booking` (confirmed Pass 2). (Decision 76, `docs/decisions/POST-SPEC-55-DECISION-LOG.md`)
- **[UNRESOLVED]** No Branch-specific field screen was ever designed (only the sidebar item and empty `branchInformation`/`updateBranch` frame ids exist) — Decision 76 confirms the field *list*, not the UI. Needs a design pass before this ships end-to-end. (Decision 76; §6.2, §12.2)
- **[CONFIRMED]** A School's `PaymentAccount` is always its own — a Franchisor has no access to it. This resolves what was previously an open question about Franchise-level vs. School-level payment-account ownership. (§6.2, §8.2, resolved Pass 2)
- **[CONFIRMED]** The platform-level `SubscriptionPlan` that a Franchise/School "subscribes to" is **ULTM8's own platform revenue** — ULTM8 billing the Franchise/School for platform access — not a plan the Franchise resells onward to its member Schools. This resolves what was previously a genuinely open, architecture-changing question. (§6.1, §10.2, resolved Pass 4)
- **[CONFIRMED]** Separately from platform `SubscriptionPlan` billing, a Franchise may charge its own member Schools a franchise fee via `Franchise.feeModel` (**Flat** or **Per-Headcount**, configurable per Franchise), collected through the dedicated `FranchiseFeeCharge` entity. This is a third, distinct payment relationship — never conflate it with a School's own `PaymentAccount` or with platform `SubscriptionPlan` billing. ULTM8 takes no cut of this charge. (§6.1, §10.2, confirmed/automated Pass 4)
- **[UNRESOLVED]** What happens to a School's `PaymentAccount`, `MembershipPlan` set, and `FranchiseFeeCharge` history if it leaves one Franchise for another, or becomes independent. Not designed — flagged rather than assumed. (§12.2, added Pass 4)

## 3. Students

- **[CONFIRMED]** Base `User` fields (shared by all customer-facing roles): email, phone (E.164 format, validated at registration), first name, surname, username (mobile only), 6-digit passcode, date of birth (ISO 8601 date, no time component), gender, nationality, language, currency, address, profile photo. (§6.1, field types resolved Pass 8, Decision 24)
- **[CONFIRMED]** Platform Admin staff are never rows in this `User` table — they live in a wholly separate `AdminUser` identity and are never joined against tenant `User` records. (§4.4, §6.1)
- **[UI BEHAVIOUR]** Mobile onboarding runs a post-registration "personalize your plan" wizard collecting gender, DOB, height/weight, and preferred activities/disciplines. This is an observed screen flow, not a stated business rule about what's mandatory vs optional — and per §14 below, this wizard alone no longer determines whether age/consent rules actually apply.
- **[CONFIRMED]** Instructor is a genuine fourth customer-facing role with its own School- and Branch-scoped login (added Pass 2, 25 Aug 2026) — not merely records that School Portal staff manage, as earlier designs implied. Provisioned by School invite, not self-registration. Permissions cover attendance scan, grading (promote/downgrade/Stripe Award, including bulk versions), and booking override only — never payments, School settings, or instructor management. (§8.2)
- **[CONFIRMED]** Branch Staff is a real Branch-scoped role, RLS-enforced on `TimetableSlot`, `Class`, `Instructor`, and `Booking`. Branch Staff has **no raw row access** to `Membership` or `Transaction` (both stay genuinely School-wide, not Branch-scopable) — only narrow, purpose-built actions: a membership-status-check returning just an active/expired signal, and the ability to resolve a cancelled Class's affected Bookings via Auto-Credit (never Auto-Refund — authorizing money leaving the business stays with School Owner/Manager). (§8.2, confirmed Pass 2/Pass 4)
- **[CONFIRMED]** `RoleGrant` — not a fixed role column — is the sole source of truth for which role(s) and scope(s) a User currently holds (`user_id`, `role`, `scope`, `granted_by`, `granted_at`, `revoked_at`). A person may hold more than one role, including the same role at more than one School (e.g. an Instructor teaching at two Schools). Sessions/JWTs are built from the full set of currently-active grants at login/refresh time. (§6.1, §8.3, confirmed Pass 2)
- **[CONFIRMED]** A minor's Student profile may instead be **Guardian-linked**, with no independent login by default. This is a distinct account model with its own confirmed rules and its own open questions — see the dedicated "Guardian accounts & ConsentRecord" section (§14) below rather than assuming it works like an ordinary Student account.
- **[UNRESOLVED]** Four unlabeled numeric stats shown on the Student/Coach Profile screens (870 / 120k / 354k / 3.8Gb). No meaning is stated anywhere in the designs. Do not guess what these represent. (§12.2)
- **[UNRESOLVED]** The "User" grouping label seen in the translations CMS (alongside Student/School/Admin) does not map to any concrete role elsewhere in the designs. The spec explicitly cautions against implementing it as a literal additional role — every concrete permission need identified is already covered by Student, School Owner/Manager, Branch Staff, Instructor, Franchise Owner, Guardian, or a Platform Admin sub-role. Treat "User" as a stale CMS grouping artifact pending confirmation. (§8.2, §12.2)

## 4. Disciplines

- **[OBSERVED IN DESIGNS]** Disciplines named in sample data: Jiu Jitsu, Karate, Judo, Krav Maga, Taekwondo, MMA, Wrestling, "etc." — the spec itself does not close this list, so treat it as illustrative, not an exhaustive enum. (§1.3)
- **[CONFIRMED]** Belt/rank progression is tracked **per discipline** — a Student can hold a different rank in each discipline they train in. (§2.3, §6.1)
- **[CONFIRMED]** A discipline is formally backed by a `Style/Discipline` entity (name, class types offered — e.g. Kids Fundamentals, Adult Sparring, Competition Team) belonging to a School, owning an ordered ladder of `Rank`s. This is validated data-model structure from the working grading-system prototype, not a Figma-only inference. (§2.3, §6.1)
- **[UNRESOLVED / TERMINOLOGY]** The spec's Figma-derived field name for what this skill calls "discipline" is `activities` (used on School, Instructor, and Class). Whether `School.activities`, `Instructor.specializations`, `Class.activities`, and the validated `Style/Discipline` entity all draw from one controlled list is still not formally reconciled in the spec. Treat "discipline" and "activity" as the same concept for narrative purposes, but do not assume they share one literal enum/table without confirming with the Architect.

## 5. Belt/rank progression

This section reflects the working, tested grading-system prototype (spec §2.3) that materially expanded the original Figma-only inference — it is engineering validation Code Studio commissioned, not something drawn in Figma, but its output is now the confirmed reference model for production.

- **[CONFIRMED]** A `Rank` belongs to a `Style/Discipline` and sits at an explicit position (`order`) in that discipline's ordered ladder. It carries a primary belt colour and an optional secondary colour (two-colour belts), a weekly class-count cap, a set of required `Skill`s, and a years-in-rank flag (see below). (§2.3, §6.1)
- **[CONFIRMED]** Stripes are modelled as an **ordered list of independent tiers** within a Rank — not a single flat stripe-count field. Each stripe tier has its own stable id (not a positional index, so reordering tiers can't break references), its own count, its own colour, its own classes-required and minimum-days-in-rank thresholds, and its own `eligibleClassTypes` list. The number of stripe tiers per belt is School-set independently per belt — there is no fixed count across the ladder (e.g. White might have 4 tiers, Blue only 2). (§2.3, §6.1)
- **[CONFIRMED]** `eligibleClassTypes` is dual-purpose — it governs both grading credit **and** class-booking eligibility (§9 below) — and is cumulative across the **flattened belt+stripe sequence** for the discipline (e.g. White-0, White-1, White-2, White-3, Blue-0, Blue-1…), so a School can let an advanced stripe tier reach directly into the next belt's class types. A School Portal validation rule requires Rank order and stripe-tier order to be unique and contiguous per discipline, since this cumulative computation depends on a well-defined sequence. (§6.1)
- **[CONFIRMED]** Once a Student reaches Black Belt or above, classes-required and minimum-days-in-rank stop applying entirely — a minimum tenure in years, tracked via the Rank's years-in-rank flag, is the sole gate instead. This is a structural difference in how the rank is evaluated, not just different numbers. (§2.3)
- **[CONFIRMED]** A Rank may additionally require specific named `Skill`s (belonging to a Style/Discipline) to be signed off, as a gate alongside — not instead of — the class-count/time-in-rank/stripe requirements. `Skill` is also referenced by `Lesson` — a many-to-many link, not a single FK (Decision 58; scoping and authorship resolved as Decision 104 — School-scoped, Instructor/Staff-authored, ordinary tenant endpoints, not Platform Admin — see `docs/decisions/POST-SPEC-55-DECISION-LOG.md`). **Doc-bug correction:** an earlier draft of this line cited "§14's video-content model" for Lesson — this skill's current §14 is Guardian accounts/ConsentRecord, unrelated; no dedicated Lesson section exists in this skill yet, see the decision-log entries above instead. (§2.3, §6.1)
- **[CONFIRMED]** `StudentRank` holds: current `Rank`, `currentStripe` (a reference to the specific stripe tier the Student sits at — resets to the new Rank's first stripe tier on every Promotion or Downgrade), date of current rank, classes attended toward the **current checkpoint** (resets to zero at every stripe or belt checkpoint — each is its own complete grading stage, not a fraction of one running belt-level count), per-skill sign-off status (**Not Started / Learning / Signed Off**) scoped to the current checkpoint only, and a computed (not stored) **readiness bucket** — exactly three values, **Ready / Almost Ready / Not Ready** — plus a computed progress %. One `StudentRank` row exists per discipline a Student trains in, and it is kept distinct from the Student's own join/member date. (§2.3, §6.1)
- **[CONFIRMED]** The **thresholds** separating Ready/Almost Ready/Not Ready, and the **formula** for progress % (previously undefined, described only as "computed"), are School-configurable per discipline — ULTM8 does not ship one fixed platform-wide formula or threshold set. (Decision 75, `docs/decisions/POST-SPEC-55-DECISION-LOG.md`)
- **[UNRESOLVED]** The actual configuration schema (what a School sets, any weighting between classes-attended and skill-sign-off ratios, and defaults offered when a School first sets up a discipline) is not yet designed — Decision 75 confirms *that* it's configurable, not the configuration mechanics themselves. (Decision 75; §6.1, §7, §12.2)
- **[OBSERVED IN DESIGNS]** The working prototype's coach-facing **Grading Board** view buckets students into **Just Starting / Getting There / Ready to Grade**, with manual drag-and-drop override for edge cases. The spec does not explicitly state whether these three UI labels are the same tiering as `StudentRank`'s confirmed Ready/Almost Ready/Not Ready enum, or a separately-labeled view over it — do not silently assume they are identical without confirming with the Architect. (§2.3)
- **[CONFIRMED]** Grading is **always coach-initiated, never automatic** — a `PromotionEvent` (types: Promotion / Downgrade / Bulk Promotion / Bulk Stripe Award / Stripe Award) is never created by the system on its own, including the moment a Student reaches a belt's highest configured stripe tier. At that point a Stripe Award simply isn't offered; the coach's only next action is a manual Promotion. What IS automatic is class-booking eligibility following a grading change — the instant `currentStripe` changes, `eligibleClassTypes` access updates immediately, with no separate unlock step. (§2.3, §6.1, §7)
- **[CONFIRMED]** Grading is permitted even when a required skill isn't yet signed off, but only behind an explicit, always-recorded written acknowledgement flag on the `PromotionEvent` — the system warns, it does not block. Multiple students can be graded in one bulk pass, each judged individually rather than as a single batch outcome. Every promotion/downgrade/award is written to an auditable rank history. (§2.3, §6.1)

## 6. Membership types

- **[CONFIRMED]** `MembershipPlan.type` now has **five** values (grown from an earlier three): **Subscription, Class Pack, Weekly Pass, Friend Pass, Trial Membership**. (§6.1)
- **[TERMINOLOGY]** "Class Pack" is the renamed successor to what was previously called "Single Pass" — the mobile Transactions screen's "One-Time" label and the earlier design-file "Drop-In" wording are the same concept under different labels. Canonical name is **Class Pack**. Don't build separate code paths for "Class Pack," "Single Pass," "One-Time," or "Drop-In."
- **[CONFIRMED]** Class Pack carries a `classesIncluded` count and may be **scoped** to one specific one-off Class (a single-class ticket, `classesIncluded=1`) or left general for repeat use across any regular Class, including School-configurable higher-credit tiers (e.g. 5-class, 10-class bundles). (§6.1)
- **[CONFIRMED]** Weekly Pass is **non-consuming** — it never sets or decrements a credit count. It grants the same unlimited access as a Subscription, governed by an expiry date instead of a recurring billing cycle. (An earlier draft incorrectly had Weekly Pass decrement `classesRemaining` like a Class Pack; this was corrected as a direct contradiction of the confirmed free-access-first booking rule, §10 below.) (§6.1)
- **[CONFIRMED]** Friend Pass is a School-gifted, **always-£0** membership type covering a guest in a Student's Booking attendee list. A Student's own Subscription/Class Pack/Weekly Pass never automatically extends to a guest — a guest is covered only if the School explicitly gifts a Friend Pass for that specific guest. Friend Pass reuses Class Pack's scoped-Class mechanism (one specific Class, or general) but is always capped at `classesIncluded=1` — no higher-tier upsell exists for Friend Pass. A School inviting the same person again, or a second friend, issues a second, separate, staff-attributed Friend Pass. (§6.1)
- **[CONFIRMED]** Trial Membership is capped at a **platform-enforced maximum of 30 days** per individual Trial (a School may still set its own shorter length within that ceiling). It is **also capped cumulatively**: total Trial days for a given Student–School pair cannot exceed 30 across a **rolling 12-month window**, closing a reissuance loophole where a School could chain back-to-back fresh Trials to dodge active-student billing indefinitely while the Student kept full access. A School can still legitimately re-trial a lapsed prospect after enough time has passed. (§6.1, §9, §10.2, Decision 54 + Decision 64)
- **[CONFIRMED]** By default, a one-off Class is **not** covered by a Student's Subscription or Weekly Pass — it always requires its own scoped Class Pack (or gifted Friend Pass) ticket. A School may opt a specific Class into general-membership access via a per-Class `membership-inclusion` flag; default is opt-out (ticket required), opt-in is a per-Class School decision. (§6.1, confirmed 25 Aug 2026)
- **[CONFIRMED]** A one-off Class's Booking still counts toward `StudentRank.classesAttended` under the same existing rule as any other Class — a Rank's `eligibleClassTypes` (§5 above) determines which class types count toward a discipline's next rank; a workshop only contributes if the School has added its class type to that discipline's curriculum. No separate mechanism exists for this. (§2.3, §6.1)

## 7. Membership billing behaviour

- **[CONFIRMED]** `MembershipPlan` fields: title, type, price, expiry, `classesIncluded` (Class Pack/Friend Pass), visibility (Public), refund-fee date, cancellation charge, terms/waiver-required flag. Belongs to School; purchased by Students as a `Membership`. (§6.1)
- **[CONFIRMED]** Cancellation/refund handling is resolved: each School sets a `class-cancellation-policy` — **Manual** (default, leaves affected credit-records for staff to resolve case-by-case), **Auto-Refund** (money back — Stripe Refund API for card payments, a manual Cash/Bank ledger reversal otherwise; the spent credit is *not* also restored), or **Auto-Credit** (the spent credit is restored to `classesRemaining`; no money moves). A Friend Pass entry is always forced to Auto-Credit regardless of School policy, since it was gifted at £0. Multi-class Class Pack refunds are computed per-credit (cumulative entitlement to date, rounded once to the currency's minor unit — not independently per partial refund). (§6.1, §10.2, resolved Pass 4)
- **[UNRESOLVED]** The *late-cancellation fee* itself is a distinct, still-open question from the refund/credit mechanism above: `Class` and `MembershipPlan` both carry a cancellation-charge field alongside a refund-fee-date cutoff, implying a Student who cancels after that cutoff may owe a fee — but whether and how that fee is actually *collected* (charged to the Student's saved card, or simply forfeited value with no new charge) is deliberately not answered by the refund/credit-mechanism decision. (§12.2, added Pass 4)
- **[CONFIRMED]** Currency conversion does not happen automatically: Student-facing `MembershipPlan` pricing is independent per-currency and School-set — a School prices in its own local currency and that is what a Student pays. ULTM8's own revenue (platform `SubscriptionPlan`, the white-label add-on, and Franchise-fee) is quoted and billed in a single anchor currency (USD), with the card network's own FX handling conversion at charge time. (§11.2, resolved Pass 5, Decision 7)
- **[CONFIRMED]** Auto-renewal applies only to **Subscription-type** Memberships, which run on a real Stripe Subscription object and therefore do recur. Class Pack, Weekly Pass, Friend Pass, and Trial are not recurring and have no renewal event — they are credit-based or date-based only. Cancelling a Subscription runs out the current paid period (no proration, no immediate cutoff) via Stripe's `cancel_at_period_end`; a downgrade to a cheaper plan takes effect at the next renewal, not immediately — both rules scoped explicitly to Subscription plans. (§6.1, §10.2, confirmed 25 Aug 2026)
- **[CONFIRMED]** A platform-wide `chargeback-pattern-restriction` background job counts a Student's **lost** Stripe disputes (`Transaction.status = Disputed` outcomes, §8 below, that resolve as lost) across **every School the Student holds a RoleGrant at** — not scoped to a single School. Once a confirmed threshold is exceeded, the Student is restricted to **Cash/Bank Transfer payment methods only**, going forward, across that same multi-School scope — the only payment methods this build supports that cannot be charged back. The Student's current School(s) are notified via the existing notification-fanout mechanism. This is a deliberate, narrow cross-tenant exception: the job computes across School boundaries by design, but a School only ever sees the resulting restriction already applied to a Student it already has legitimate visibility into — never another School's raw dispute data. **The specific threshold count is a business/implementation parameter that is not stated anywhere in the confirmed material — do not invent or infer a number.** This is a distinct mechanism from, and does not close, the separate Trial-reissuance/account-recreation gap (§6 above): a Student can still evade this restriction by registering a fresh account, which resets the count to zero — an accepted, unclosed loophole, not something this decision claims to fix. (§9, §12.1 Decision 68)

## 8. Membership states and transitions

- **[CONFIRMED — corrected]** `Membership.status` has **exactly two values: Active and Expired.** An earlier design/draft stage showed a third value, "Pending," but this was removed entirely (Decision 6, Pass 5) after it produced a real bug (a £0 Friend Pass, with no Transaction ever created, would have been stuck Pending forever). **Do not model a Pending Membership state.** The on-screen "Pending" label some Figma screens show is a design-file artifact — the real Pending status lives on `Transaction`/`Invoice` (see below), not on `Membership`. (§6.1, §9, §10.2, resolved Pass 5)
- **[CONFIRMED]** `Transaction`/`Invoice` has its own, separate status enum — **Successful / Pending / Failed / Refunded / Disputed** — which must not be confused with `Membership.status`. A `Transaction` can sit Pending (e.g. an unconfirmed Cash/Bank Transfer) while no `Membership` row exists yet at all. (§6.1, §10.2)
- **[CONFIRMED]** A `Membership` row is **created** (not status-flipped from some prior state) at the exact moment its payment settles, always Active: any Stripe charge succeeding (a one-time PaymentIntent for Class Pack/Weekly Pass/Trial, or a Subscription) creates it immediately via the `stripe-webhook-processing` job. A Cash/Bank Transfer purchase creates only a Pending `Transaction` first (no Membership yet); School Owner/Manager staff (not Branch Staff) confirm it via a dedicated endpoint that atomically flips the Transaction to Successful and creates the Membership Active in the same step. Any Cash/Bank-eligible plan priced at £0 skips the wait entirely and is created Active immediately, since there's nothing to confirm. (§6.1, §9, §10.2, resolved Pass 5)
- **[CONFIRMED]** A Student cannot hold two simultaneous **Active general-access** Memberships (Subscription or Weekly Pass) at the same School — this is validated at the moment of creation, not just at checkout-click time. (§6.1)
- **[CONFIRMED]** Active → Expired is driven by one of several confirmed mechanisms, not a single uniform trigger: (a) **live-computed, date-based expiry** for Class Pack/Friend Pass/Weekly Pass/Trial — evaluated at every access/booking check against the stored expiry date, not flipped by a scheduled job; (b) for a Subscription, voluntary cancellation runs out the paid period then Expires (with future Bookings after that date swept/cancelled), and a failed renewal stays Active through Stripe's own retry window (`past_due`) and only Expires once Stripe's retries are exhausted — the same sweep mechanism handles both cases; (c) credit exhaustion (0 `classesRemaining`) for credit-based types; (d) a **lost** Stripe dispute force-Expires the Membership outright (and, for a Subscription, additionally cancels the underlying Stripe Subscription object). An Auto-Credit that lands on an already-Expired Membership reactivates it only if it expired from hitting 0 credits — not if its own expiry date had already passed. (§6.1, §9, §10.2, Decisions 26 & 55)

## 9. Classes

- **[CONFIRMED]** `Class` fields: title, activities, banner image, description, start/end date, capacity (nullable positive integer; null = unlimited), booking-end date/time, QR-attendance-end date/time, refund-fee date, cancellation charge, terms/waiver-required flag, and a `membership-inclusion` flag (§6 above) opting the Class into general-membership access. Belongs to School; taught by an Instructor; has many Bookings. (§6.1)
- **[CONFIRMED]** `TimetableSlot` ↔ `Class` relationship is resolved: a bookable `Class` row is **either** materialized ahead of time from an active, recurring `TimetableSlot` (via the `class-occurrence-generation` job, on a rolling schedule) **or** created directly as an independent, one-off event that bypasses `TimetableSlot` entirely. Do not assume every Class must trace back to a TimetableSlot. (§6.1, §7, §9, confirmed 24 Aug 2026)
- **[CONFIRMED]** `Class.terms/waiver-required` is enforced at **Booking creation** — creating a Booking on such a Class also requires a **Signed** `WaiverSignature` for that Student. This was previously an unwired gap (the flag and the waiver entities existed but nothing connected them) and is now closed. (§6.1, closed by logic review 25 Aug 2026)
- **[CONFIRMED]** Class booking is additionally **rank-gated**: a Rank/stripe tier's `eligibleClassTypes` (§5 above) governs which class types a Student may book, cumulative by ladder order. This is a hard block by default; an Instructor/Staff member can override per Booking (`overriddenBy` + `overrideReason`, always recorded). An override bypasses the rank gate only — never Class capacity; an override on a Full Class still routes through the waitlist below. (§6.1, confirmed/corrected 25 Aug 2026)
- **[CONFIRMED]** A Class's "Full" status counts **every attendee across all Bookings**, including Friend Pass guests on the attendee list — not raw Booking count. (§6.1, confirmed 25 Aug 2026)
- **[CONFIRMED]** There is **no walk-in attendance path**: a Student must hold a pre-existing Booking before attending: QR check-in only ever matches against an existing Booking, never creates one. (§6.1, resolved 25 Aug 2026)

## 10. Bookings

- **[CONFIRMED]** `Booking` fields: class date/time, status (**Upcoming / Completed / Cancelled / No-Show** — four values; No-Show added to close a state-machine gap, see below), `sourceMembershipId` (which Membership's credit this Booking drew against), attendee list (Figma field name: `whoJoinYou`), and — added for multi-attendee/refund correctness — an `overriddenBy`/`overrideReason` pair (rank-gate override, §9 above) and a `refundResolution`/`resolvedBy` pair per credit-record. Belongs to a Student and a Class. (§6.1)
- **[CONFIRMED]** Creating a Booking requires the Student to hold an **Active** Membership for that School. If the Student holds more than one Active Membership, a non-consuming general-access one (Subscription/Weekly Pass) is checked and spent **first**, so a paid Class Pack/Friend Pass credit is never spent unnecessarily. (§6.1, confirmed/logic-reviewed 25 Aug 2026)
- **[CONFIRMED]** A credit (and the booked seat) is **reserved the moment a Booking is created**, not at attendance. This closed a real bug where a no-show previously consumed nothing, allowing a Class Pack to be re-booked indefinitely without ever showing up, and allowing phantom overbooking. Cancelling before the Class's cancellation-charge cutoff refunds/credits it back (§7 above); a No-Show does not. (§6.1, §9, closed by logic review 25 Aug 2026)
- **[CONFIRMED]** `Booking.status` gains **No-Show**: set by a background job once a Class's end time (or QR-attendance-end time) passes with the Booking still Upcoming. This does not touch `StudentRank.classesAttended` and does not refund/restore the spent credit. (§6.1, §9, added by logic review 25 Aug 2026)
- **[CONFIRMED — resolved]** `whoJoinYou` attendee-list semantics: each additional attendee beyond the Student requires **either** their own valid Membership **or** a School-gifted Friend Pass for that specific guest — a Student's own Class Pack/Subscription does not cover guests automatically. Each attendee-list entry carries its own `membershipId`, `refundResolution`, and `resolvedBy`, since a single Booking can draw against several different Memberships at once (the Student's own, plus one Friend Pass per guest). (§6.1, resolved/corrected 25 Aug 2026)
- **[CONFIRMED]** A new `WaitlistEntry` entity handles Full Classes: FCFS `position`, status (**Waiting / Notified / Claimed / Expired / Cancelled**), `joinedAt`, `notifiedAt`, `claimByDeadline` (based on the School's `waitlistClaimWindow` setting, default 120 minutes, capped by the Class's own start time). Costs no credit while Waiting — only becomes a real Booking, and only then draws a credit, once Claimed. A freed seat (from a Cancellation or a No-Show alike) notifies the next Waiting entry; an unclaimed window cascades to the next person in position order. (§6.1, §7, §9, confirmed 25 Aug 2026)

This was previously flagged as an important unresolved gap in an earlier draft of this skill — it is resolved as of 24 Aug 2026. ## 12. QR check-in

- **[CONFIRMED]** A camera-based QR scan screen (`qrCode`) exists on the Student mobile app for class attendance. (§2.2)
- **[CONFIRMED]** `Class` carries a QR-attendance-end date/time field — a bounded window during which check-in is valid. (§6.1)
- **[CONFIRMED]** A `qr-attendance-processing` background job is triggered by a QR scan at check-in, and what a **successful** scan writes is now fully specified: it marks the matching Booking Completed and increments `StudentRank.classesAttended` (§11 above) — there is no separate Attendance entity. (§9)
- **[UNRESOLVED, with a binding constraint]** What the QR code itself actually displays, and who generates/shows it, is still unresolved as a **screen** — the School Portal sidebar's "QR Code" nav item has no corresponding designed screen anywhere in the Figma files. However, a binding constraint now applies to whenever it *is* designed: it must be a **time-boxed, rotating** code for the duration of the Class occurrence, never a single static code for the whole occurrence — closing a photograph-and-send-remotely spoofing vector that exists today. Do not design or build a static per-Class QR code. The Instructor/Staff-scoped booking-override endpoint remains the accessibility/no-alternative fallback regardless of how this resolves. (§2.2, §6.1, §7, §12.2, Decision 66)
- **[CONFIRMED]** Specification 55's `InstructorsModule` endpoint list carries a second, distinct scan endpoint, `POST /classes/{id}/attendance-scan`, sitting beside the confirmed Instructor/Staff-scoped override endpoint (§9 above) and separate from the self-service `POST /attendance/scan`. This is now confirmed as a real, intentional **Instructor-operated roll-call scan** — self-service and Instructor roll-call scanning are both real, coexisting check-in paths, not one superseding the other. The Instructor/Staff-scoped override endpoint (§9 above) stays scoped to the accessibility/no-alternative exception path only, unchanged by this decision. (Decision 71, `docs/decisions/POST-SPEC-55-DECISION-LOG.md`)
- **[UNRESOLVED]** Decision 71 confirms the roll-call scan's *purpose*, not its mechanics: what the Instructor actually scans (a Student's own code vs. some other mechanism), whether it's per-Student or batched per-Class, and what deters an Instructor marking Students who aren't present are all still undesigned. None of the confirmed consent/liveness protections built for self-service (Decision 66, Decision 69) have been extended to this path yet — do not build it from assumption. Needs an engineering design pass from the Architect before backend work starts. (Decision 71; §7, §12.2)

- **[CONFIRMED]** `Waiver` fields: title, body text, per-school assignment. Belongs to School; has many `WaiverSignature`s. (§6.1)
- **[CONFIRMED]** `WaiverSignature` fields: signer full name, signature, signed date, status — exactly four values: **Signed, Unsigned, Expired, Pending**. Belongs to a Waiver and a Student. (§6.1)
- **[CONFIRMED]** The e-signature mechanism as designed is a **typed full name plus a signature field** — there is no drawn/biometric signature capture or additional verification step shown. (§2.2)
- **[CONFIRMED — resolved]** `Class.terms/waiver-required` is now wired into booking eligibility: Booking creation on such a Class requires a **Signed** `WaiverSignature` for that Student. This was previously an unresolved enforcement-point gap; it is resolved. (§6.1, closed by logic review 25 Aug 2026)
- **[CONFIRMED]** An unverified, self-reported date of birth can no longer silently bypass Guardian consent requirements: whether a Student is self-attested-adult by DOB, or must be Guardian-linked, is checked at the **first consequential action** — a Membership purchase, a booking-triggered payment, or waiver-signing, whichever comes first — not merely at registration or in the optional onboarding wizard. If the check fails, that action is blocked with a redirect toward proper Guardian-linked enrollment; an existing independent account is never retroactively migrated into a Guardian-linked one. See §14 below for the full Guardian/consent model this protects. (§2.2, §6.1, §8.2, Decision 67)
- **[CONFIRMED]** The waiver e-signature mechanism — typed full name plus drawn signature capture (Decision 74), for both Student and Guardian signers — has been legally reviewed and confirmed sufficient, across every market ULTM8 operates in. This closes what was previously an unevaluated legal-sufficiency gap sharpened (not resolved) by Decision 67. ## 14. Guardian accounts & ConsentRecord

This is new domain material confirmed since the original draft of this skill — a Guardian is not a variant of Student, and its rules do not fall out of anything in §3 above.

- **[CONFIRMED]** `Guardian` is a full-adult customer-facing account (own login, own React Native app session) with full access to its own profile plus **every linked minor Student profile**: payment method, waiver-signing authority, bookings, and memberships for each linked minor. (§6.1, §8.2)
- **[CONFIRMED]** A linked minor Student profile (name, DOB, rank) has **no independent login by default**. It may optionally get a **limited login** — provisional age threshold **13**, *pending legal review* — granting **read-only** access to the minor's own schedule/rank only, never payment or waiver capability. (§6.1, §8.2)
- **[CONFIRMED]** The age-13 limited-login threshold and the age-18 age-of-majority threshold have been legally reviewed and confirmed as final, across every market ULTM8 operates in — no longer provisional placeholders. (Decision 77, `docs/decisions/POST-SPEC-55-DECISION-LOG.md`)
- **[UNRESOLVED]** Whether a linked-Student login under the (now-confirmed) age-13 threshold can directly request the mobile Permissions screen's Device Location/Contacts/Calendar/Camera access, or whether those must stay gated behind the Guardian's own account. Not settled by Decision 77, which resolves only the age numbers themselves. (§6.1, §8.2, §11.5, §12.2)
- **[CONFIRMED]** At the age of majority, the person **self-registers a fresh, independent Student account** — the linked minor profile is never migrated into it, and there is no reverse migration path either (an independent account is never retroactively converted into a Guardian-linked one — see the DOB entry-guard rule in §13 above). This is a deliberate one-way-only model. (§6.1, §8.2, confirmed 25 Aug 2026)
- **[CONFIRMED]** Revoking or deleting a Guardian account **cascades** `revoked_at` onto every linked minor's own `RoleGrant` — a minor's limited login can never outlive the Guardian relationship that authorized it. (§6.1, §8.2, Decision 28)
- **[CONFIRMED]** `ConsentRecord` is a new, first-class, auditable, revocable consent entity — distinct from `WaiverSignature` (see the terminology table, §16). Fields: Guardian reference, linked-minor (Student) reference, `policyVersion` (the specific privacy-notice/data-practice description consented to — a new data-collecting feature requires fresh consent under a new `policyVersion`, never silent inheritance), timestamp, and status (**Active / Withdrawn**, with its own withdrawal timestamp). It is deliberately not COPPA-specific — built to the general shape shared by GDPR Art. 8, UK-GDPR, and LGPD (verifiable, revocable, tied to a specific description of data use). Verification reuses the Guardian's own already-OTP-verified account as the consent context. (§6.1, §8.2, Decision 57)
- **[CONFIRMED]** `ConsentRecord` carries **two tiers**, not one: a **baseline** tier covering the general account/attendance/grading data every Guardian-linked minor account requires, and a separate **camera** tier tied specifically to QR-check-in camera use and profile-photo capture (mirroring the fact that OS-level camera permission is a single per-app grant, not scopable per feature). Location, Contacts, and Calendar are deliberately **not** modeled as their own tiers, since no confirmed feature uses any of them yet — a tier would be added only if and when one of those becomes a real, confirmed feature. (§6.1, §12.2, Decision 57)
- **[CONFIRMED]** Consent withdrawal is **proportional to tier**, not uniform: withdrawing **baseline** consent triggers the full cascade — the same `RoleGrant`-revocation cascade as Guardian-account revocation, plus the account-deletion-processing job, scoped to that one Student. Withdrawing **camera-tier-only** consent (with baseline remaining Active) does **not** delete the account or touch grading history — it marks only that `ConsentRecord` Withdrawn, blocks future self-service QR check-in for that Student (enforced server-side, not merely by hiding the UI option), and clears any already-stored profile photo. The Instructor/Staff-scoped booking-override endpoint becomes that Student's ongoing check-in path. (§6.1, §7, §9, Decision 69 — this corrected an earlier version of the rule that force-deleted the whole account on *any* withdrawal, disproportionate for a camera-only preference.)
- **[UNRESOLVED]** No consent-management interface — a screen for a Guardian to withdraw either tier, or even view current consent status — exists anywhere in the confirmed designs. `ConsentRecord`'s backend behavior is fully specified for whenever such a screen is built, but a Guardian currently has **no confirmed way to exercise any consent right at all.** Needs a design decision and a Guardian-facing screen before this ships to any market carrying children's-data-protection law. (§12.2, added Pass 8)
- **[UNRESOLVED]** No non-camera self-service check-in alternative exists for a Student whose camera-tier consent is withdrawn (or who has an accessibility need blocking QR scan) — the Instructor/Staff override endpoint is the only fallback, and it was sized for occasional accessibility use, not as a standing per-class mechanism. Flagged as a real product opportunity (e.g. a short entry-code alternative), not built around a guess. (§7, §12.2, Decision 69)
- **[UNRESOLVED]** Whether Guardian-specific actions (consent withdrawal, reuse of a saved payment method) warrant their own step-up-authentication extension. The Owner-tier step-up MFA (Decision 12) doesn't cover Guardian at all — Decision 57 deliberately reuses the Guardian's ordinary OTP-verified login as the consent context, so the app-level biometric re-lock (Decision 61) is the *only* mechanism standing between an unlocked device and a Guardian's saved-payment purchase or a consent change affecting someone else's child. Not decided. (§12.2, §12.1 Decisions 12/57/61)

## 15. Business invariants

These are the standing rules that should hold true across the whole system, drawn only from what's confirmed elsewhere in this document:

- A School may exist with no Franchise at all; code must never assume `Franchise` is present. **[CONFIRMED]**
- A Student's belt rank is discipline-scoped; a student can simultaneously hold different ranks in different disciplines. **[CONFIRMED]**
- `Membership.status` has exactly two values, Active and Expired — a Membership is *created* Active at the moment its payment settles, never status-flipped from a Pending state, because no such state exists on `Membership`. **[CONFIRMED — see §8 for the full model and the distinct `Transaction.status` enum that does include Pending.]**
- A belt/stripe grading action (Promotion, Downgrade, Stripe Award, or their Bulk equivalents) is always coach-initiated — the system never auto-promotes or auto-awards a stripe, including when a Student reaches a belt's highest configured stripe tier. **[CONFIRMED — see §5.]**
- Attendance has no dedicated entity — a QR scan marks the matching Booking Completed, and that Completed status is what drives `StudentRank.classesAttended`. **[CONFIRMED — see §11.]**
- Instructor is a genuine customer-facing role with its own School/Branch-scoped login, provisioned by School invite — not merely a record managed by School staff. **[CONFIRMED — see §3.]**
- A Franchise's fee income from its member Schools (`FranchiseFeeCharge`) is a wholly separate payment relationship from platform `SubscriptionPlan` billing and from a School's own `PaymentAccount` — never conflate the three. **[CONFIRMED — see §2.]**
- Platform Admin staff are never represented in the customer-facing `User` table, and customer data must never be reachable through the Platform Admin identity except through the audited, explicitly-namespaced admin surface. **[CONFIRMED — business-level restatement of §4.4; implementation mechanics live in `ultm8-tenant-isolation`, not here.]**
- One School's data is never visible to another School or Franchise, by business expectation as well as by architecture. **[CONFIRMED — the *mechanism* (Row-Level Security) is a technical concern owned by `ultm8-tenant-isolation`; this skill only asserts the business expectation.]**
- ULTM8 does not have the technical ability to view a School's live payment credentials in plaintext (Stripe Connect / secrets-manager custody only). **[CONFIRMED — business-level restatement of §9.4/§10.4; mechanics live in `ultm8-payments`.]**
- A School's white-label branded app is created only while its `SubscriptionPlan.whiteLabelApp` entitlement is active; on downgrade or cancellation, the app is frozen at its last build rather than removed. **[CONFIRMED, §5.5]**
- `MembershipPlan`/`Membership` (School↔Student billing) and `SubscriptionPlan` (platform↔Franchise/School billing) are two separate entities and must never be merged or used interchangeably in code, copy, or database design. **[CONFIRMED distinction; see next section.]**
- A Guardian's `ConsentRecord` withdrawal is proportional to tier — camera-only withdrawal must never trigger full account deletion. **[CONFIRMED — see §14.]**

## 16. Canonical terminology

Use these terms consistently; several are easy to conflate because the Figma source data uses inconsistent labels, or because the spec renamed a concept mid-review.

| Canonical term | Meaning | Do not confuse with |
|---|---|---|
| `MembershipPlan` / `Membership` | School charging a Student (Subscription / Class Pack / Weekly Pass / Friend Pass / Trial) | `SubscriptionPlan` |
| `SubscriptionPlan` (platform) | Franchise/School's own billing relationship with ULTM8 — confirmed as ULTM8's own platform revenue | `MembershipPlan`; also not `FranchiseFeeCharge` |
| `FranchiseFeeCharge` | A Franchise's own fee charged to its member Schools (Flat or Per-Headcount) | `SubscriptionPlan` (platform↔Franchise/School) or a School's own `PaymentAccount` |
| Class Pack | The renamed canonical name for a one-time membership purchase | "Single Pass" / "One-Time" / "Drop-In" — all superseded labels for the same concept |
| Weekly Pass | A non-consuming, time-boxed-unlimited membership type gated by an expiry date | Class Pack (credit-consuming) or Subscription (recurring Stripe billing) |
| Friend Pass | An always-£0, School-gifted guest membership, capped at one guest/one visit | A Student's own Membership automatically covering a guest — it never does |
| Discipline | A martial art / activity a School offers and a Student trains in | `activities` is the literal Figma field name for the same idea — not formally reconciled, see §4 |
| `PaymentAccount` | A School's own configured payment method (Stripe Connect account id, or manual Cash/Bank Transfer) | Not a Student's saved card — that's a Stripe PaymentMethod on the Student's own profile; also not a Franchise-level account, since a School's PaymentAccount is always its own |
| `Transaction`/`Invoice` | A ledger row for a completed or pending charge, with its own Successful/Pending/Failed/Refunded/Disputed status | `Membership` (the ongoing entitlement, Active/Expired only — see §8) or `Booking` (the class reservation) |
| `RoleGrant` | The sole source of truth for a User's role(s) and scope(s) | Not a fixed "role" column — a User may hold several grants at once |
| `AdminUser` | Platform Admin staff identity, separate realm | `User` (customer-facing: Student, School staff, Instructor, Guardian) |
| `Guardian` | The adult account holding payment/waiver authority for one or more linked minors | The linked minor's own Student profile, which has no independent login by default |
| `ConsentRecord` | A Guardian's data-collection consent for a linked minor (platform-scoped, two-tiered) | `WaiverSignature` — School-authored liability/assumption-of-risk text (School-scoped), a different legal concept entirely |
| `TenantAppConfig` | A School's white-label branding/build config, only exists when entitled | Not a School's general profile/settings |

## 20. Rules for how other AI agents must use this skill

5. **Cite section references (§) when asserting a rule** in code comments, PR descriptions, or agent output, so a human reviewer can trace it back to source in one step.
6. **Do not treat Figma sample/placeholder values** (specific belt names, prices, the "IMAS" brand name, discipline lists marked "etc.") **as confirmed business constants.** They illustrate the UI; they are not a spec.
7. **Only the Architect agent may edit this skill.** Any other agent that discovers a gap, contradiction, or newly-needed rule should report it upward, not patch this file directly.
