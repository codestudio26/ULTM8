# v1.2 backend backlog — frontend redesign follow-ups

Running, append-only list built up as each page gets redesigned and
implemented for real (v1). Every entry here is something the *real* v1 page
shows as an honest placeholder — never a fabricated value — because no
backend field, endpoint, or business rule exists for it yet. v1.2 is where
these get designed and built for real.

**Process:** when a page is implemented for real, list every element that
had to be shown as a placeholder ("—", disabled, decorative) because the
backend doesn't support it. Don't guess at *how* to build the fix here —
that's a v1.2 design pass of its own, and several of these overlap with
`[UNRESOLVED]` items already flagged in `skills/ultm8-domain-rules/SKILL.md`
(cross-referenced below where that's the case) — check there before
designing a fix, per that skill's own escalation rule.

  elsewhere.

  here") still has no entity, endpoint, or decision log entry anywhere —
  same unresolved status as when it was first flagged mid-canvas.
- **The two "Get the app" QR tiles** specifically depend on `apps/student`

### Add / Update Instructor pages (designed against the template you sent —
`InstructorCreate.pdf`/`instructorUpdate.pdf`; not yet built)

Verified field-for-field against `CreateInstructorDto`/`UpdateInstructorDto`
(`apps/api/src/instructors/dto/`) before designing anything. `Instructor`
only ever persists: `userId` (create-only), `branchId`, `photoUrl`,
`beltRanking` (free text), `specializations[]`, `phone`,
`yearsOfExperience`, `bio` — nothing else. Every field below is something
the template shows that this real surface can't back yet:

- **Instructor Name + Email Address as typed/editable fields** — not real.
  An Instructor profile isn't a new identity; it's a profile attached to an
  *existing* User who already holds an active Instructor `RoleGrant`
  (granted first on the Staff page). The real, already-shipped create flow
  is a picker of those eligible Users (`GET
  .../instructors/eligible-users`), not free-typed Name/Email — and the
  picked User's name/email can never be edited from here at all, on
  create or update.
  **Update (28 Sep) — new capability requested:**
  per direct, repeated feedback, Add Instructor now also shows an
  "Add Manually" mode (First name / Surname / Email) as an alternative to
  the eligible-User dropdown. This is materially different from anything
  else on this page — it isn't attaching a profile to an existing User,
  it's **creating a brand-new User account from a Staff-entered name +
  email**. Confirmed no precedent exists anywhere in ULTM8 for this: even
  the real Invite flow (Decision 116) only performs an exact-match
  *lookup* of an account that already exists; nothing creates one. Real
  self-registration (`AuthService.register()`) collects far more (phone,
  passcode, DOB, etc.) than Name + Email alone could satisfy.
  **Update (28 Sep):** per direct request, the logic for this was written
  up as **Decision 206** — a proposed account-claim invitation (Staff
  submits name/email → an email with a single-use, expiring claim link
  goes out → the person completes the rest of real registration
  themselves behind that link, and the Instructor role + profile are
  created automatically once they do).

  **DONE (12 Oct 2026) — built, but to a different, later-approved design
  that supersedes Decision 206, not that one.** Decision 206's
  account-claim design was itself approved for build the next day
  (Decision 211, 10 Oct), but superseded one day later, before being
  built, when the product owner was asked this exact question again in a
  separate session and chose a different, incompatible mechanism —
  **Decision 237** ("Instructor 'Add Manually': real record created
  immediately, system passcode emailed, forced change on first login —
  supersedes Decision 206/211"). Decision 237 is what actually shipped:
  - **`POST schools/:schoolId/instructors/add-manually`**
    (`apps/api/src/instructors/instructors.controller.ts`,
    `CreateInstructorManuallyDto`) creates a real `User` + `RoleGrant` +
    `Instructor` row **immediately** from just `firstName`/`surname`/
    `email` (plus `branchId` when the School has branches) — no
    invite/acceptance step, no claim link. `InstructorsService.createManually()`
    generates a random 6-digit temp passcode, hashes it, and sets
    `User.mustChangePasscode = true`.
  - **The temp passcode is emailed** (not an invite link) — the existing
    email-delivery path, non-blocking: creation always succeeds even if
    the email send fails (`emailSent: false` on the response), matching
    the shape `CoachInvitesService.create()` already established.
  - **A forced passcode change is enforced on first login** via
    `User.mustChangePasscode`/`POST /auth/passcode-change/first-login`,
    a narrow single-purpose token that can call no other endpoint.
  - **Frontend:** `apps/school-portal/src/instructors/AddInstructorManuallyModal.tsx`
    — First name / Surname / Email (+ Branch, required only when the
    School has branches), unchanged in shape from the 28 Sep mockup.
  - **Everything else stays blank at creation, by the product owner's own
    answer** ("only Name and Email are required at creation... everything
    else is left blank and the instructor fills it in themselves after
    their first login") — see the Address/Activities/Certification/
    consent correction below for where that now actually happens.
  - **Decision 206's `AccountInvitation` entity was never built** and
    Decision 211 (which had approved it for build) was superseded before
    any of it shipped — this is a real, built-vs-discarded-design
    history, not a gap to still close. Decision 237 explicitly leaves
    open whether `AccountInvitation` should still be built for Staff's own
    identical from-zero-invite gap on `StaffPage.tsx` — that remains
    unresolved, but separately from Instructor "Add Manually," which this
    entry now closes.
- **Address / Activities / Certification / consent — correction (12 Oct
  2026): these fields now exist on `Instructor`, but not on this modal.**
  Decision 217 (10 Oct) approved building all four; they're real schema
  columns today — `Instructor.address` (String?), `Instructor.activities`
  (String[], deliberately distinct from `specializations[]`),
  `Instructor.certificationKey` (R2 object key, via Decision 218's
  S3-compatible upload pipeline), `Instructor.certificationConsentedAt`

  self-service page the Instructor fills in themselves after their own
  first login** — `CompleteInstructorProfilePage.tsx`

- **Ranking — correction (12 Oct 2026): `beltRanking` no longer exists.**

### Invite to Instructor Role page — **now built**

Added after direct feedback that "Add Instructor" (a picker over Users who
*already* hold the Instructor role) has no path for a School Owner who
wants to bring in someone who doesn't hold that role yet, and no way to
locate them by email/phone if they're not yet an eligible option in that
dropdown. Resolved as a dedicated modal reachable from
`InstructorsPage.tsx` (`InviteToInstructorRoleModal.tsx`, a third button —
"Invite existing user" — beside "Add manually"/"Add instructor", not the
split "+" menu this entry originally sketched; a plain third button
matches how the other two entry points are already presented on this same
page, so all three stay consistently one tap away rather than hidden a
level deeper), deliberately matching how `StaffPage.tsx`'s own invite flow
already works — not a "create a person from zero" flow, since nothing in
this codebase supports that (see below).

- **No new endpoint needed for the core mechanics.** The lookup
  (`GET schools/:schoolId/role-grants/invite-candidate`, exact email/phone
  match only, Decision 116) and the grant itself (`POST` via
  `RoleGrantsService.create()`, Decision 80/81, hardcoded to role=
  `INSTRUCTOR` on this page) are both real and already shipped — this page
  just reuses them in an Instructor-scoped, two-step form, the same
  find-then-confirm shape `StaffPage.tsx` already uses.
- **Candidate email isn't actually returned by the lookup — resolved.**
  `InviteCandidateResponseDto` now also carries `email` (`null` when
  `found: false`, same nullable shape as `firstName`/`surname`), so the
  mockup's "Found: {name}" card and "an invite email would be sent to
  {{candidateEmail}}" copy can both use a real value.
- **No "invite an unregistered person" capability exists anywhere in
  ULTM8.** Confirmed by reading `lookupInviteCandidate` directly: it's an
  exact match against `User` rows that already exist. There is no flow
  anywhere in this codebase — Staff or otherwise — that creates an account
  for someone who has never registered. If a true from-zero invite (send a
  link to an unregistered email/phone, auto-create their account on
  acceptance) is wanted, that's a new capability, not a gap in this page.
- **Granting a role sent no notification — resolved.**
  `RoleGrantsService.create()` now sends a "you've been granted this role"
  email (Postmark primary, AWS SES fallback — already-wired
  `NotificationDeliveryService`, Spec 55 §11.4) on every grant it creates,
  Instructor or Branch Staff alike — not scoped to this page alone, since
  neither role had its own separate notification anywhere else. Non-blocking,
  same `emailSent: false`-on-failure shape `CreateInstructorManuallyResponseDto`/
  `CreatedCoachInviteResponseDto` already established (new
  `CreatedRoleGrantResponseDto`); `StaffPage.tsx`'s pre-existing invite form
  now surfaces the same flag. **WhatsApp isn't a channel this codebase
  has at all** — no provider, no integration, not mentioned anywhere in
  Spec 55 — so it was ruled out rather than built toward.
- **SMS is not a channel this codebase can send today, either — confirmed
  by reading the code, not assumed.** Twilio *is* integrated
  (`apps/api/src/auth/otp/twilio-verify.service.ts`), but its own header
  comment scopes it deliberately to Twilio's **Verify** product for OTP
  codes only (registration/passcode-recovery) — "the purpose-built OTP
  product, not Twilio's generic Messaging API" (Spec 55 §11.4). There is no
  general-purpose SMS-sending capability anywhere in ULTM8. Per direct
  decision: ship the email trigger above now; **a text-message option (and
  any email/text choice in the UI) is a separate, future decision** that
  would need a new integration — Twilio's Messaging API or another SMS
  provider — including its own cost/deliverability/opt-in questions, none
  of which are evaluated anywhere in Spec 55 today.
- Decided directly with the user: the invite stays **two-step**, matching
  the Staff precedent exactly — it only finds the person and grants the
  role. Belt/specializations/bio are filled in afterward as a separate
  step (the person then appears in Add Instructor's dropdown), not
  collected in the same form.

## Students page (v1 shipped, read-only — `StudentsPage.tsx`; Invite — shipped (existing-person path only, see its own update below); Detail — designed, not yet built)

Verified directly against the real code before designing anything: there is
**no dedicated Student entity/module** anywhere in the backend — a Student
is a `User` holding an active `STUDENT` RoleGrant at a School (same shape
Instructors' own eligible-users endpoint already establishes for
`INSTRUCTOR`). `StudentsPage.tsx`'s own header comment states the create/
edit gap explicitly, not as an oversight: *"there is no create/edit flow
here, since a Staff member doesn't create a Student profile directly: a
Student joins a School themselves (or a Guardian enrolls a linked minor),
both via the STUDENT RoleGrant path (`SchoolsService.join()`)... not this
page."* This traces to Decision 96 for the self-enrollment half only —
Decision 96 is titled "an adult caller joining on their own behalf only"
and explicitly states under "What this does NOT resolve": Guardian-on-
behalf-of enrollment is "not solved here." Guardian-on-behalf-of enrollment
was added afterward (Phase 38, `SchoolsService.join()`'s `isGuardianAction`
branch, commit `e87825b`) and has no numbered Decision of its own — it's
documented only in passing inside Decision 118. Every gap below was checked
against this before being logged.

### Invite a Student (shipped — existing-person path only; see "Update" below)

**Update (12 Oct):** built, matching exactly the scope the 28 Sep update
below settled on — find-then-confirm, someone who already has a ULTM8
account. `SchoolsService.join()` gained a Staff-on-behalf-of branch

`apps/school-portal/src/students/InviteStudentPage.tsx`
(`/students/invite`, linked from `StudentsPage.tsx`).

Left genuinely open, flagged rather than guessed: this still has no
"add a brand-new person" path at all — Instructors' own "Add manually"
(`CreateInstructorManuallyDto`/`createManually()`) has no Student
equivalent. Whether one should be added here, despite this exact removal
below, is a real product question for the product owner, not re-decided
unilaterally in either direction by this update.

**Update (28 Sep):** replaces the earlier "Enroll a Student" mockup
(`StudentAdd.dc.html`, an Adult/Minor manual-creation form extending
Decision 206's account-claim invitation design) — removed per direct
feedback that a from-scratch account-creation flow was the wrong shape for
this page. `StudentInvite.dc.html` follows the same find-then-confirm
pattern as **Invite to Instructor Role**, scoped only to someone who
**already has** a ULTM8 account but hasn't joined this School yet — not a
from-zero account-creation flow.

- **The lookup is real, not proposed.** `GET
  schools/:schoolId/role-grants/invite-candidate` (Decision 116) is a
  generic exact email/phone match against `User` via `PrismaAuthService`
  — verified directly by reading `lookupInviteCandidate`: it does not
  filter by role at all, so it's reusable here exactly as built for
  Instructor, with zero changes.
- **The enroll step is Proposed — and a materially different, narrower gap
  than the removed page's.** The `STUDENT` RoleGrant is created exclusively

  `RoleGrantsService.create()`, whose `GRANTABLE_ROLES` is `INSTRUCTOR`/

  `assertSchoolOwner` in place of `assertGuardianOfStudent`) — not a change

  removed page's account-creation-plus-claim-link machinery.

  (`SchoolsService.join()` grants `schoolId`-only, matching
  `RoleGrant.branchId` being unused on the `STUDENT` path).
- No email-on-grant note here — unlike Instructor Invite, this page

  *any* `SIGNED` `WaiverSignature` at that School, not one scoped to a
  specific required Waiver (`Class` has no field linking it to one
  particular `Waiver` — only the boolean `termsWaiverRequired`). Whether
  "requires a waiver" should mean "any waiver at this School" or "this
  School's one canonical waiver" or something else is worth the Architect
  confirming explicitly rather than leaving it as an implicit consequence
  of the schema's current shape.

## Notifications page (mockup — "Notifications — 5 concepts", Concept 3 Priority Inbox favored)

Verified directly against `NotificationsController`/`NotificationsService`/
`schema.prisma`'s `Notification` model before designing anything. The real
API surface here is the narrowest of any page redesigned this session:
`GET /notifications/me` (list, self-scoped) and
`PATCH /notifications/:id/read` (mark read) — that's the whole write
surface. Every item below is something a concept board shows that this
real surface can't back yet.

- **Compose/broadcast a message to Students (Concept 4 — Broadcast
  Center)** — the single biggest gap of any page this session. There is
  no endpoint anywhere for a School Owner/Staff member to author and send
  a notification. Every real `Notification` row is written only by the
  internal `notification-fanout` background job, itself only ever
  triggered by three system events (a Waiver assigned, a payment dispute,
  a chargeback-pattern restriction) — never by a direct API call. Building
  this for real needs, at minimum: a new endpoint (e.g.
  `POST /schools/:schoolId/notifications/broadcast`), School-Owner-gated
  same as Waiver/MembershipPlan CRUD; an audience parameter (all Students
  at the School is the obvious default — whether to support narrower
  targeting, e.g. by Branch or Class, is a real product question, not a
  Developer default to invent); and enqueuing through the existing
  `notification-fanout` queue rather than a new delivery path, reusing the
  per-recipient job-dedup pattern `WaiverSignatureRequestsProcessor`
  already established.
- **Snooze (Concept 3 — Priority Inbox)** — shown, disabled-styled, in the
  row's action menu. `Notification` has no snoozed/deferred state of any
  kind in the schema (`read` is the only status-like field). Needs a
  product decision on shape (a `snoozedUntil` timestamp column plus a job
  to un-snooze it back into the unread list, most likely) before any
  endpoint design makes sense.
- **Delete (Concept 3 — Priority Inbox)** — shown, disabled-styled, same
  menu. No `DELETE /notifications/:id` (or equivalent) exists anywhere in
  `NotificationsController`. Mechanically the simplest of these gaps to
  close, once it's decided whether a User should be able to hard-delete
  their own notification history at all (no precedent either way in this
  codebase's other modules).
- **Push delivery rate (Concept 5 — Delivery Ribbon)** — shown as a
  placeholder tile. `DeviceToken` registration is real (`POST`/`DELETE
  /notifications/device-tokens`), but actual push SEND (FCM/APNs dispatch)
  is, per the `DeviceToken` model's own header comment, "deliberately NOT
  built this phase." There's also no delivery-status field on
  `Notification` to report a rate from even once SEND exists.
- **Read within 24h (Concept 5 — Delivery Ribbon)** — shown as a
  placeholder tile. `Notification.read` is a live boolean, not a
  timestamped event (no `readAt` column), so a time-to-read metric can't
  be computed even after the fact from what the schema stores today —
  this needs a schema change (a `readAt` column set the first time
  `markRead` fires), not just a new aggregation endpoint over existing
  columns.
- ~~**True total/unread counts (Concept 5 — Delivery Ribbon)**~~ — **CLOSED.**
  `GET /notifications/me/counts` (self-scoped, same convention as
  `GET /notifications/me`) now returns `{ total, unread }` computed
  server-side over the caller's full set of `Notification` rows, not
  whatever page happens to be loaded client-side. `NotificationsPage.tsx`
  wires this into a real two-tile stats ribbon (Total/Unread), same
  `StatTile` pattern Transactions/Membership Plans already established.
  Push delivery rate and Read within 24h (both also shown on the Concept 5
  mockup) remain unbuilt — see the two items above this one.

**Concepts 1 (Refined Table) and 2 (Grouped Timeline) have no backend
gap** — every element on both is a real field or a client-side
computation over real fields (a Type label mapped from the real,
free-string `Notification.type`, and a relative-time/day-grouping display
computed from the real `Notification.createdAt`), same as Concept 2 for
Transactions.

## Update Student page (`StudentUpdate.dc.html`) — whole page is a proposed new capability

Unlike `InstructorUpdate.dc.html` (a genuinely real, wired `PATCH
/instructors/:id` — Instructor is a School-owned record Staff can edit),
**no backend capability exists today for a School Owner/Staff member to
edit a Student's profile on the Student's behalf.** Verified directly, not
assumed, before building this page:

- A Student has no dedicated table — it's a `User` row plus an active
  `STUDENT`-role `RoleGrant` (`apps/api/prisma/schema.prisma`, `model
  User`'s own header comment: role is "NEVER a column here").
- The only profile-edit endpoint anywhere is `PATCH /users/me`
  (`apps/api/src/users/users.controller.ts`, `apps/api/src/users/dto/
  update-user.dto.ts`) — explicitly **self-service only**, scoped to the
  caller's own `user.sub`. There is no `:id`-param variant and no Staff/
  Owner-authorized path to it.
- `StudentSummaryResponseDto` (the roster list's own DTO) exposes only
  `id`, `firstName`, `surname`, `email`, `enrolledAt` — none of the other
  fields this mockup shows (phone, date of birth, gender, nationality,
  language, currency, address, profile photo) are resolved onto any
  Student-facing page anywhere in this canvas today.
- There is also no single-Student detail endpoint
  (`GET /schools/:id/students/:studentId`) — only the School-wide roster
  list exists.
- Guardian routes (`apps/api/src/guardians/guardians.controller.ts`) are
  explicitly scoped to the calling Guardian's own data only, by their own
  header comment — no on-behalf-of shape for any other caller, Student
  profile editing included.

Every field on `StudentUpdate.dc.html` is real on `User` (confirmed via
`UpdateUserDto`'s own field list: firstName, surname, username (mobile-only),
dateOfBirth, gender, nationality, language, currency, address,
profilePhotoUrl — email/phone deliberately excluded there too, as unique
login/OTP identifiers), but the whole *page* — a Staff-facing edit surface
for a Student's profile — is a proposed new capability, not a build-out of
something already wired. Closing this gap needs, at minimum: a new
`PATCH /schools/:id/students/:studentId` (or equivalent) endpoint, a
Staff-authorization check (the `assertStaffAtSchool`-equivalent every
other Staff-facing Student/Instructor mutation already uses), and reuse of
`UpdateUserDto`'s field set rather than a new DTO. `StudentDetail.dc.html`'s
new "Edit Profile" button links here, tagged with this same caveat in its
own tooltip.

### Three judgment calls made explicitly (not product-confirmed, flagged here)
- **(a) No mockup was available to build against.** `Dashboard.dc.html`
  exists only in the external design-canvas tool this build couldn't reach
  from this repo checkout — not in this repo, and not retrievable from any
  claude.ai artifact link checked either. The product owner gave explicit
  go-ahead to design the layout fresh rather than wait on it (see this
  feature's own PR description for a written walkthrough of the resulting
  layout, since there is no mockup to diff it against). The product owner is
  expected to review the real page and ask for revisions directly.
- **(b) Activities are grouped by the raw `Class.activities` string tag, not
  canonicalized.** This matches the exact convention already established in
  `apps/api/src/classes/dto/classes-query.dto.ts`'s own `activities` filter
  (the `has`/`hasSome` Prisma operator on the raw array) — Decision 90's
  bridge, not the newer canonical `Discipline`/`styles` FK (Decision 152/173)
  that booking rank-gating has since moved to. Differently-cased or
  differently-spelled tags for the same real discipline show as separate
  buckets; this is the same known, separately-tracked gap SKILL.md §4/
  Decision 90 already flags, not reopened or newly discovered here. A Class
  with no `activities` tags at all falls into a sentinel `"Unspecified"`
  bucket rather than silently vanishing from the breakdown.
- **(c) A Booking whose Class carries more than one activity tag counts once
  PER TAG** (fan-out) in the per-activity breakdown — a Class tagged both
  "Judo" and "BJJ" shows that Booking under both — but counts exactly once in
  that day's own total and in the response's overall total. This means a
  day's `activities[].totalBookings` summed can exceed that day's own
  `totalBookings`; this is deliberate, not a bug, and is documented on
  `BookingsSummaryResponseDto` itself. A genuinely different attribution
  (e.g. splitting credit fractionally across tags, or picking only the
  Class's first tag) was considered and rejected as no more "correct" and
  harder to reason about from the response alone.
