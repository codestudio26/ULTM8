# v1.2 backend backlog — frontend redesign follow-ups

Running, append-only list built up as each page gets redesigned and
implemented for real (v1). Every entry here is something the *real* v1 page
shows as an honest placeholder — never a fabricated value — because no
backend field, endpoint, or business rule exists for it yet. v1.2 is where
these get designed and built for real.

**Process:** when a page is implemented for real, list every element that
had to be shown as a placeholder ("—", disabled, decorative) because the
backend doesn't support it. Don't guess at *how* to build the fix here —
that's a v1.2 design pass of its own, and several of these overlap with
`[UNRESOLVED]` items already flagged in `skills/ultm8-domain-rules/SKILL.md`
(cross-referenced below where that's the case) — check there before
designing a fix, per that skill's own escalation rule.

## Membership Plans page (v1 shipped — `MembershipPlansPage.tsx`, Stats Ribbon direction)

- **"Active members" stat tile** — shown as a visibly disabled/muted
  placeholder ("—") in the new stats ribbon above the plans table. No
  per-plan (or per-School) membership-count/aggregation endpoint exists
  anywhere: `MembershipsController` only has `findMyMemberships` and
  `getMembershipStatus`, both Student-scoped reads, nothing that counts
  active Memberships against a MembershipPlan or a School. Total/Visible/
  Hidden plan counts on the same ribbon ARE real — computed client-side
  from the already-fetched plans list, no new endpoint needed for those
  three.
- **Codegen gap, not a Membership-Plans-specific one** — found while wiring
  the ribbon's inline Visibility toggle: `UpdateMembershipPlanDto`'s
  generated TS type (`packages/api-client/src/generated/schema.d.ts`) marks
  `visible`/`termsWaiverRequired` as non-optional, even though the OpenAPI
  schema itself has no `required` array for this DTO at all (confirmed by
  exporting a fresh schema from the current backend source — both fields
  are genuinely optional there, matching `MembershipsService.updatePlan()`'s
  own undefined-tolerant handling). `openapi-typescript` appears to treat
  any `@ApiPropertyOptional({ default })` field this way — grepped the
  whole schema for other `default`-having properties absent from their
  DTO's `required[]` and found the same pattern on ~10 more DTOs:
  `CreateSchoolDto`/`UpdateSchoolDto` (`classCancellationPolicy`,
  `waitlistClaimWindowMinutes`), `CreateFranchiseDto`/`UpdateFranchiseDto`
  (`feeModel`), `CreateClassDto`/`UpdateClassDto` (`termsWaiverRequired`,
  `membershipInclusion`), `CreateTimetableSlotDto`/`UpdateTimetableSlotDto`
  (`status`, `termsWaiverRequired`, `membershipInclusion`),
  `CreateRankDto`/`UpdateRankDto` (`yearsInRankFlag`), `GradingActionDto`
  (`acknowledgeWithoutSkillSignoff`). Worked around locally in
  `membershipPlanQueries.ts` with a single documented type cast rather than
  widened ad hoc everywhere — the real fix (upgrading/configuring
  `openapi-typescript`, or dropping `default` from the affected Swagger
  metadata) is a one-time tooling/codegen change, not a per-DTO one, so it's
  listed here once rather than under every affected page.

## Timetable page (mockup — click-to-book preview, Daily/Weekly/Monthly)

- **"Book" action on every slot** — a click-to-book preview was added to
  every rendered slot across all three views (agenda cards on Daily/Weekly,
  dots on Monthly). It opens a confirmation dialog (Class, Instructor,
  Day-or-Date, Time, Branch, Cancel/Confirm) but Confirm only closes the
  dialog — there's no real submission, because **no backend booking
  capability exists for a Timetable slot at all.**
- **Blocking architectural gap, not just a missing endpoint** —
  `skills/ultm8-domain-rules/SKILL.md` §9 already flags this
  `[UNRESOLVED]`: "How `TimetableSlot` and `Class` actually relate... do
  not assume one Class row is auto-spawned per TimetableSlot occurrence
  without this being confirmed." The real `Booking` entity belongs to
  `Class` (§10, §16: `Class *—* Booking`), not `TimetableSlot` — this page
  deliberately renders `TimetableSlot`, the recurring weekly template (see
  the page's own subtitle: "not the bookable Classes list"). Building a
  real "book from the Timetable" flow needs this relationship resolved by
  the Architect first — e.g. does selecting a slot resolve to an existing
  dated `Class`/occurrence for that weekday, or does one need to be
  created/looked up on demand — before any endpoint design makes sense.
- **Once that's resolved,** the confirmation shape itself (Class,
  Instructor, Class Timings, Class Date) is already confirmed —
  Spec §3.2's own booking flow describes exactly those fields plus payment
  if required, so the mockup's dialog fields don't need to change, only
  what they're wired to.

## Waivers page (v1 shipped — `WaiversPage.tsx`, Split-Pane Reader direction)

- **Per-waiver signature status ("has this been signed, by whom, and who's
  outstanding")** — requested by the user; not built, shown instead as a
  single visibly-inert "Signatures" panel (dashed border, muted text,
  explanatory tooltip) in the reader pane. Three separate, independently-
  blocking gaps, layered — each needs to be closed before the next one is
  even useful:
  1. **No staff-facing endpoint exists.** `WaiversController` only exposes
     `POST /waivers/:id/sign` (Student/Guardian signs),
     `POST /waivers/:id/signature-upload-url`, and `GET /waivers/me`
     (Student-self, own signatures only). Nothing lets a School Owner list
     `WaiverSignature` rows for a Waiver or a School. A new endpoint is
     needed — e.g. `GET /schools/:schoolId/waivers/:id/signatures`,
     School-Owner-gated (same gate as Waiver CRUD), returning each
     signature's signer name, signed date, and status.
  2. **`WaiverSignature` has no concept of "unsigned" today, even once (1)
     is built.** `WaiversService.sign()` is the only code path that ever
     creates a row, and `schema.prisma` declares
     `status WaiverSignatureStatus @default(SIGNED)` — nothing anywhere
     ever writes `UNSIGNED`/`PENDING`/`EXPIRED` on this model, despite
     those being real enum values. A row's mere existence currently means
     "signed." Showing "who hasn't signed" needs either (a) a real
     Student roster to diff signed rows against (see next point), or (b) a
     product decision to start writing an explicit
     Unsigned/Pending row per assignment (a data-model change, an
     Architect decision, not a Developer default to invent here).
  3. **The Student roster itself has no real population path in
     production yet** — a separate, larger, already-tracked gap
     (`WaiverSignatureRequestsProcessor`'s own header comment, Decision 95,
     and the project roadmap): no endpoint anywhere creates a `STUDENT`
     RoleGrant through the real API; every e2e test seeds one directly
     with a superuser Prisma client. Until Student enrollment is real, even
     a correct signature-status endpoint would have no real Student list
     to compute a denominator against.
  Recommended display shape once all three are resolved (confirmed with
  the user via AskUserQuestion): a rollup count (e.g. "12 of 40 signed"),
  expandable to a full per-Student roster with each Student's name and
  Signed/Unsigned/Expired/Pending status.
- **Related, newly-confirmed real behavior worth reconciling with
  `skills/ultm8-domain-rules/SKILL.md` §13** — its `[UNRESOLVED]` note on
  where `Class.terms/waiver-required` is enforced is actually resolved in
  code: `BookingsService` checks at booking time whether the Student holds
  *any* `SIGNED` `WaiverSignature` at that School, not one scoped to a
  specific required Waiver (`Class` has no field linking it to one
  particular `Waiver` — only the boolean `termsWaiverRequired`). Whether
  "requires a waiver" should mean "any waiver at this School" or "this
  School's one canonical waiver" or something else is worth the Architect
  confirming explicitly rather than leaving it as an implicit consequence
  of the schema's current shape.
