# v1.2 backend backlog — frontend redesign follow-ups

Running, append-only list built up as each page gets redesigned and
implemented for real (v1). Every entry here is something the *real* v1 page
shows as an honest placeholder — never a fabricated value — because no
backend field, endpoint, or business rule exists for it yet. v1.2 is where
these get designed and built for real.

**Process:** when a page is implemented for real, list every element that
had to be shown as a placeholder ("—", disabled, decorative) because the
backend doesn't support it. Don't guess at *how* to build the fix here —
that's a v1.2 design pass of its own, and several of these overlap with
`[UNRESOLVED]` items already flagged in `skills/ultm8-domain-rules/SKILL.md`
(cross-referenced below where that's the case) — check there before
designing a fix, per that skill's own escalation rule.

### Add / Update Instructor pages (designed against the template you sent —
`InstructorCreate.pdf`/`instructorUpdate.pdf`; not yet built)

Verified field-for-field against `CreateInstructorDto`/`UpdateInstructorDto`
(`apps/api/src/instructors/dto/`) before designing anything. `Instructor`
only ever persists: `userId` (create-only), `branchId`, `photoUrl`,
`beltRanking` (free text), `specializations[]`, `phone`,
`yearsOfExperience`, `bio` — nothing else. Every field below is something
the template shows that this real surface can't back yet:

- **Instructor Name + Email Address as typed/editable fields** — not real.
  An Instructor profile isn't a new identity; it's a profile attached to an
  *existing* User who already holds an active Instructor `RoleGrant`
  (granted first on the Staff page). The real, already-shipped create flow
  is a picker of those eligible Users (`GET
  .../instructors/eligible-users`), not free-typed Name/Email — and the
  picked User's name/email can never be edited from here at all, on
  create or update.
  **Update (28 Sep) — new capability requested, genuinely unresolved:**
  per direct, repeated feedback, Add Instructor now also shows an
  "Add Manually" mode (First name / Surname / Email) as an alternative to
  the eligible-User dropdown, tagged Proposed/Placeholder throughout. This
  is materially different from anything else on this page — it isn't
  attaching a profile to an existing User, it's **creating a brand-new
  User account from a Staff-entered name + email**. Confirmed no precedent
  exists anywhere in ULTM8 for this: even the real Invite flow (Decision
  116) only performs an exact-match *lookup* of an account that already
  exists; nothing creates one. Real self-registration
  (`AuthService.register()`) collects far more (phone, passcode, DOB,
  etc.) than Name + Email alone could satisfy.
  **Update (28 Sep):** per direct request, the logic for this is now
  written up — **Decision 128** in
  `docs/decisions/POST-SPEC-55-DECISION-LOG.md` proposes an account-claim
  invitation (Staff submits name/email → an email with a single-use,
  expiring claim link goes out → the person completes the rest of real
  registration themselves — phone, passcode, date of birth — behind that
  link, and the Instructor role + profile are created automatically once
  they do). It's a **proposed design, not approved or built** — flagged
  there for Architect/product-owner confirmation, same as every other
  Developer-level inference in that log. This bullet stays `[UNRESOLVED]`
  as real backend work until that decision is confirmed and implemented —
  it's a new auth-adjacent capability (new entity, two new unauthenticated
  endpoints, a new frontend screen), not a small addition to
  `CreateInstructorDto`.
  **Priority — not a peripheral gap:** per direct instruction, this is
  core to Add Instructor, not a nice-to-have alongside it. Without Decision
  128 (or something equivalent) built, "Add Manually" is decorative —
  Staff can type a name and email, but the person created has no way to
  ever log in, so the whole mode does not actually work end-to-end. This
  should be treated as a blocking dependency of "Add Manually" shipping
  for real, not scheduled independently of it.
- **Address** — no such field exists anywhere on `Instructor`.
- **Activities (to Instruct Within)**, as a field distinct from
  Specializations — there is only one list (`specializations[]`); no
  second, separate "activities" array exists on `Instructor`.
- **Latest Certification (file upload)** — no certification field, and no
  file-upload/storage capability of any kind exists on `Instructor`.
- **Terms and conditions / Agreement to follow the app's guidelines /
  Liability waivers (checkboxes)** — no consent-tracking model or fields
  exist anywhere for an Instructor. (Not to be confused with the Student-
  facing `WaiverSignature` model, which is unrelated and already covered

- **Ranking**, shown in the template as a dropdown — the real field
  (`beltRanking`) is free text only (e.g. "Black Belt, 3rd Dan"), not a
  structured/enumerated ranking system. Building an actual belt/rank

  than a display string) is a real backend decision, not a Developer
  default — flagged again here since it directly affects how reliably the
  belt icon (built for the Instructors list/table pages) can render for
  arbitrary real data; see also the next point.
- **Photo upload** — `photoUrl` is a real, persisted field, but there is no
  real image-upload pipeline anywhere in this app yet (school-portal-wide,

  string. **Update (28 Sep):** per direct request, Add/Update now present

### Instructor Detail page (designed against `instructorInformation.pdf`;
not yet built)

- **Email address** — `InstructorResponseDto` resolves the linked User's
  `firstName`/`surname` (via `resolveUserNames`) but not `email`. Showing
  a real email on this page needs that same resolution extended to
  include it.
- **"Instructor Class" grid (classes this Instructor teaches)** —
  confirmed there is no dedicated endpoint (no `GET
  /instructors/:id/classes`, no `instructorId` filter on `GET
  schools/:schoolId/classes`). Buildable today only by fetching the
  School's full Classes list and filtering client-side — and the filter
  has to match `Instructor.userId` against `Class.instructorId`, since
  that FK points at `User.id`, not `Instructor.id`. Real per-class fields
  available once filtered: title, activities, `bannerUrl`, description,
  startDate, capacity. **Not available even then:** a live "X of Y
  booked" enrolled count (no endpoint returns one cheaply; would need a
  per-class booking-count call) — the template's "12/30" is decorative. A
  real dedicated `GET /instructors/:id/classes` endpoint (School-scoped,
  returning the enrolled count already computed server-side) would be the
  proper v1.2 fix rather than the client-side-filter workaround.
- **Two separate images (large cover banner + small school-logo badge)** —
  `Instructor` has exactly one photo field (`photoUrl`). A real second
  "cover banner" field (e.g. `bannerUrl`, matching the pattern `Class`
  already has) would need to be added if this two-image layout is wanted
  for real. **Update (28 Sep):** a Banner Image field was briefly added
  here and to Add/Update as a Proposed placeholder, then removed entirely
  per direct request — all three Instructor pages now show only the one
  real `photoUrl` avatar, matching what the backend actually supports.
  This bullet is kept as a historical note in case a real cover-banner
  field is revisited later, not as a currently-shown gap.
- Same Address / Activities / Certification / consent-checkbox gaps as the
  Add/Update pages above, since this page displays the same profile.

### Invite to Instructor Role page (new — not yet built)

Added after direct feedback that "Add Instructor" (a picker over Users who
*already* hold the Instructor role) has no path for a School Owner who
wants to bring in someone who doesn't hold that role yet, and no way to
locate them by email/phone if they're not yet an eligible option in that
dropdown. Resolved as a separate page reachable from a split "+" menu on
Instructors (Add Instructor / Invite to Instructor Role), deliberately
matching how `StaffPage.tsx`'s own invite flow already works — not a
"create a person from zero" flow, since nothing in this codebase supports
that (see below).

- **No new endpoint needed for the core mechanics.** The lookup
  (`GET schools/:schoolId/role-grants/invite-candidate`, exact email/phone
  match only, Decision 116) and the grant itself (`POST` via
  `RoleGrantsService.create()`, Decision 80/81, hardcoded to role=
  `INSTRUCTOR` on this page) are both real and already shipped — this page
  just reuses them in an Instructor-scoped, two-step form, the same
  find-then-confirm shape `StaffPage.tsx` already uses.
- **No "invite an unregistered person" capability exists anywhere in
  ULTM8.** Confirmed by reading `lookupInviteCandidate` directly: it's an
  exact match against `User` rows that already exist. There is no flow
  anywhere in this codebase — Staff or otherwise — that creates an account
  for someone who has never registered. If a true from-zero invite (send a
  link to an unregistered email/phone, auto-create their account on
  acceptance) is wanted, that's a new capability, not a gap in this page.
- **Granting a role sends no notification today.** Read directly:
  `RoleGrantsService.create()` only writes the `RoleGrant` row — no email,
  SMS, or push fires. Per direct request, this page's mockup shows a
  "Grant Instructor Role & Send Invite" action and a success state
  mentioning an invite email, both tagged Proposed/Placeholder. The
  recommended real channel is **email** — Postmark (primary) + AWS SES
  (fallback) are already wired for other notifications
  (`NotificationDeliveryService`, Spec 55 §11.4) — this just needs a new
  trigger on role-grant creation. **WhatsApp isn't a channel this codebase
  has at all** — no provider, no integration, not mentioned anywhere in
  Spec 55 — so it was ruled out rather than built toward.
- **SMS is not a channel this codebase can send today, either — confirmed
  by reading the code, not assumed.** Twilio *is* integrated
  (`apps/api/src/auth/otp/twilio-verify.service.ts`), but its own header
  comment scopes it deliberately to Twilio's **Verify** product for OTP
  codes only (registration/passcode-recovery) — "the purpose-built OTP
  product, not Twilio's generic Messaging API" (Spec 55 §11.4). There is no
  general-purpose SMS-sending capability anywhere in ULTM8. Per direct
  decision: ship the email trigger above now; **a text-message option (and
  any email/text choice in the UI) is a separate, future decision** that
  would need a new integration — Twilio's Messaging API or another SMS
  provider — including its own cost/deliverability/opt-in questions, none
  of which are evaluated anywhere in Spec 55 today.
- Decided directly with the user: the invite stays **two-step**, matching
  the Staff precedent exactly — it only finds the person and grants the
  role. Belt/specializations/bio are filled in afterward as a separate
  step (the person then appears in Add Instructor's dropdown), not
  collected in the same form.

## Membership Plans page (v1 shipped — `MembershipPlansPage.tsx`, Stats Ribbon direction)

- **"Active members" stat tile** — shown as a visibly disabled/muted
  placeholder ("—") in the new stats ribbon above the plans table. No
  per-plan (or per-School) membership-count/aggregation endpoint exists
  anywhere: `MembershipsController` only has `findMyMemberships` and
  `getMembershipStatus`, both Student-scoped reads, nothing that counts
  active Memberships against a MembershipPlan or a School. Total/Visible/
  Hidden plan counts on the same ribbon ARE real — computed client-side
  from the already-fetched plans list, no new endpoint needed for those
  three.
- **Codegen gap, not a Membership-Plans-specific one** — found while wiring
  the ribbon's inline Visibility toggle: `UpdateMembershipPlanDto`'s
  generated TS type (`packages/api-client/src/generated/schema.d.ts`) marks
  `visible`/`termsWaiverRequired` as non-optional, even though the OpenAPI
  schema itself has no `required` array for this DTO at all (confirmed by
  exporting a fresh schema from the current backend source — both fields
  are genuinely optional there, matching `MembershipsService.updatePlan()`'s
  own undefined-tolerant handling). `openapi-typescript` appears to treat
  any `@ApiPropertyOptional({ default })` field this way — grepped the
  whole schema for other `default`-having properties absent from their
  DTO's `required[]` and found the same pattern on ~10 more DTOs:
  `CreateSchoolDto`/`UpdateSchoolDto` (`classCancellationPolicy`,
  `waitlistClaimWindowMinutes`), `CreateFranchiseDto`/`UpdateFranchiseDto`
  (`feeModel`), `CreateClassDto`/`UpdateClassDto` (`termsWaiverRequired`,
  `membershipInclusion`), `CreateTimetableSlotDto`/`UpdateTimetableSlotDto`
  (`status`, `termsWaiverRequired`, `membershipInclusion`),
  `CreateRankDto`/`UpdateRankDto` (`yearsInRankFlag`), `GradingActionDto`
  (`acknowledgeWithoutSkillSignoff`). Worked around locally in
  `membershipPlanQueries.ts` with a single documented type cast rather than
  widened ad hoc everywhere — the real fix (upgrading/configuring
  `openapi-typescript`, or dropping `default` from the affected Swagger
  metadata) is a one-time tooling/codegen change, not a per-DTO one, so it's
  listed here once rather than under every affected page.

## Timetable page (mockup — click-to-book preview, Daily/Weekly/Monthly)

- **"Book" action on every slot** — a click-to-book preview on every
  rendered slot across all three views (agenda cards on Daily/Weekly, dots
  on Monthly). **Correction (Decision 127):** an earlier version of this
  note said "no backend booking capability exists for a Timetable slot at
  all" — that overstated the gap. `BookingsService.bookClass()` already
  has a real, shipped Staff-on-behalf-of path (a School Owner/Staff member
  can book a named Student into a **Class**, gated by
  `assertStaffAtSchool`), and the confirmation dialog's Student field is
  now wired to that reality — its options are real-shaped, from the real
  `GET /schools/:id/students` roster. The dialog requires a Student be
  selected before "Confirm" enables, matching what a real submission would
  need. Confirm still only closes the dialog, though — no booking is
  actually created — because of the gap below, which is the one part that
  was never overstated.
- **Blocking architectural gap, not just a missing endpoint** —
  `skills/ultm8-domain-rules/SKILL.md` §9 already flags this
  `[UNRESOLVED]`: "How `TimetableSlot` and `Class` actually relate... do
  not assume one Class row is auto-spawned per TimetableSlot occurrence
  without this being confirmed." `bookClass()` takes a `classId`, and the
  real `Booking` entity belongs to `Class` (§10, §16: `Class *—* Booking`),
  not `TimetableSlot` — this page deliberately renders `TimetableSlot`,
  the recurring weekly template (see the page's own subtitle: "not the
  bookable Classes list"). Building a real "book from the Timetable" flow
  needs this relationship resolved by the Architect first — e.g. does
  selecting a slot resolve to an existing dated `Class`/occurrence for
  that weekday, or does one need to be created/looked up on demand —
  before any endpoint design makes sense. This is the only remaining
  blocker; the Student-picker and the underlying Staff-booking capability
  are not.
- **Once that's resolved,** the confirmation shape itself (Student, Class,
  Instructor, Class Timings, Class Date) is already confirmed —
  Spec §3.2's own booking flow describes exactly those fields plus payment
  if required, so the mockup's dialog fields don't need to change, only
  what they're wired to.

## Waivers page (v1 shipped — `WaiversPage.tsx`, Split-Pane Reader direction)

- **Per-waiver signature status ("has this been signed, by whom, and who's
  outstanding")** — requested by the user; not built, shown instead as a
  single visibly-inert "Signatures" panel (dashed border, muted text,
  explanatory tooltip) in the reader pane. Three separate, independently-
  blocking gaps, layered — each needs to be closed before the next one is
  even useful:
  1. **No staff-facing endpoint exists.** `WaiversController` only exposes
     `POST /waivers/:id/sign` (Student/Guardian signs),
     `POST /waivers/:id/signature-upload-url`, and `GET /waivers/me`
     (Student-self, own signatures only). Nothing lets a School Owner list
     `WaiverSignature` rows for a Waiver or a School. A new endpoint is
     needed — e.g. `GET /schools/:schoolId/waivers/:id/signatures`,
     School-Owner-gated (same gate as Waiver CRUD), returning each
     signature's signer name, signed date, and status.
  2. **`WaiverSignature` has no concept of "unsigned" today, even once (1)
     is built.** `WaiversService.sign()` is the only code path that ever
     creates a row, and `schema.prisma` declares
     `status WaiverSignatureStatus @default(SIGNED)` — nothing anywhere
     ever writes `UNSIGNED`/`PENDING`/`EXPIRED` on this model, despite
     those being real enum values. A row's mere existence currently means
     "signed." Showing "who hasn't signed" needs either (a) a real
     Student roster to diff signed rows against (see next point), or (b) a
     product decision to start writing an explicit
     Unsigned/Pending row per assignment (a data-model change, an
     Architect decision, not a Developer default to invent here).
  3. **The Student roster itself has no real population path in
     production yet** — a separate, larger, already-tracked gap
     (`WaiverSignatureRequestsProcessor`'s own header comment, Decision 95,
     and the project roadmap): no endpoint anywhere creates a `STUDENT`
     RoleGrant through the real API; every e2e test seeds one directly
     with a superuser Prisma client. Until Student enrollment is real, even
     a correct signature-status endpoint would have no real Student list
     to compute a denominator against.
  Recommended display shape once all three are resolved (confirmed with
  the user via AskUserQuestion): a rollup count (e.g. "12 of 40 signed"),
  expandable to a full per-Student roster with each Student's name and
  Signed/Unsigned/Expired/Pending status.
- **Related, newly-confirmed real behavior worth reconciling with
  `skills/ultm8-domain-rules/SKILL.md` §13** — its `[UNRESOLVED]` note on
  where `Class.terms/waiver-required` is enforced is actually resolved in
  code: `BookingsService` checks at booking time whether the Student holds
  *any* `SIGNED` `WaiverSignature` at that School, not one scoped to a
  specific required Waiver (`Class` has no field linking it to one
  particular `Waiver` — only the boolean `termsWaiverRequired`). Whether
  "requires a waiver" should mean "any waiver at this School" or "this
  School's one canonical waiver" or something else is worth the Architect
  confirming explicitly rather than leaving it as an implicit consequence
  of the schema's current shape.

## Notifications page (mockup — "Notifications — 5 concepts", Concept 3 Priority Inbox favored)

Verified directly against `NotificationsController`/`NotificationsService`/
`schema.prisma`'s `Notification` model before designing anything. The real
API surface here is the narrowest of any page redesigned this session:
`GET /notifications/me` (list, self-scoped) and
`PATCH /notifications/:id/read` (mark read) — that's the whole write
surface. Every item below is something a concept board shows that this
real surface can't back yet.

- **Compose/broadcast a message to Students (Concept 4 — Broadcast
  Center)** — the single biggest gap of any page this session. There is
  no endpoint anywhere for a School Owner/Staff member to author and send
  a notification. Every real `Notification` row is written only by the
  internal `notification-fanout` background job, itself only ever
  triggered by three system events (a Waiver assigned, a payment dispute,
  a chargeback-pattern restriction) — never by a direct API call. Building
  this for real needs, at minimum: a new endpoint (e.g.
  `POST /schools/:schoolId/notifications/broadcast`), School-Owner-gated
  same as Waiver/MembershipPlan CRUD; an audience parameter (all Students
  at the School is the obvious default — whether to support narrower
  targeting, e.g. by Branch or Class, is a real product question, not a
  Developer default to invent); and enqueuing through the existing
  `notification-fanout` queue rather than a new delivery path, reusing the
  per-recipient job-dedup pattern `WaiverSignatureRequestsProcessor`
  already established.
- **Snooze (Concept 3 — Priority Inbox)** — shown, disabled-styled, in the
  row's action menu. `Notification` has no snoozed/deferred state of any
  kind in the schema (`read` is the only status-like field). Needs a
  product decision on shape (a `snoozedUntil` timestamp column plus a job
  to un-snooze it back into the unread list, most likely) before any
  endpoint design makes sense.
- **Delete (Concept 3 — Priority Inbox)** — shown, disabled-styled, same
  menu. No `DELETE /notifications/:id` (or equivalent) exists anywhere in
  `NotificationsController`. Mechanically the simplest of these gaps to
  close, once it's decided whether a User should be able to hard-delete
  their own notification history at all (no precedent either way in this
  codebase's other modules).
- **Push delivery rate (Concept 5 — Delivery Ribbon)** — shown as a
  placeholder tile. `DeviceToken` registration is real (`POST`/`DELETE
  /notifications/device-tokens`), but actual push SEND (FCM/APNs dispatch)
  is, per the `DeviceToken` model's own header comment, "deliberately NOT
  built this phase." There's also no delivery-status field on
  `Notification` to report a rate from even once SEND exists.
- **Read within 24h (Concept 5 — Delivery Ribbon)** — shown as a
  placeholder tile. `Notification.read` is a live boolean, not a
  timestamped event (no `readAt` column), so a time-to-read metric can't
  be computed even after the fact from what the schema stores today —
  this needs a schema change (a `readAt` column set the first time
  `markRead` fires), not just a new aggregation endpoint over existing
  columns.
- **True total/unread counts (Concept 5 — Delivery Ribbon)** — the
  ribbon's Total/Unread tiles are real, but only reflect the
  currently-loaded page: no dedicated count endpoint exists on
  `GET /notifications/me`, so a true School-wide (or even just
  caller-wide) total needs either a new count endpoint or fetching every
  page client-side, which this mockup deliberately doesn't do.

**Concepts 1 (Refined Table) and 2 (Grouped Timeline) have no backend
gap** — every element on both is a real field or a client-side
computation over real fields (a Type label mapped from the real,
free-string `Notification.type`, and a relative-time/day-grouping display
computed from the real `Notification.createdAt`), same as Concept 2 for
Transactions.
