# Front desk: backend handover

**Date:** 27 Oct 2026 · **Frontend:** built (this branch, `feature/front-desk-check-in`) · **Design:** `DESIGN.md` → "Check-in and front-desk mode" · **Rules:** Decisions 304, 315, 316, 317, 318, 320, 351, 362, 365 · **Build list:** `docs/v1.3-backend-backlog.md` §3.1, §3.2, §3.5, §3.21

## What's built and works today

The School Portal has both front-desk screens, built on the API that already exists:

| Screen | Route | Uses (all existing endpoints) |
|---|---|---|
| **Students → Check-in** (staff) | `/check-in` (owners: a tab next to Students; coaches and Branch Staff: a menu item) | `GET /schools/{id}/classes?startsFrom&startsTo`, `GET /classes/{id}/bookings`, `GET /schools/{id}/students?search=`, `GET /students/{id}/membership-status`, `GET /students/{id}/eligibility`, `POST /classes/{id}/book` (staff on behalf), `POST /classes/{id}/attendance-scan` |
| **Front-desk mode** (the tablet) | `/front-desk` (full screen) | The same calls, made with the staff member's own login |

**What works now:**
- Today's classes, with places left and checked-in counts.
- **Scan** the QR in the student's app:
  - The student id is read from the token only to open the right card.
  - The API verifies the token on check-in, and records the check-in as `INSTRUCTOR_SCAN`.
- **Name** search, recorded as `INSTRUCTOR_MANUAL`.
- **Welcome card** showing:
  - membership status;
  - belt progress ("N of M classes to the next belt");
  - today's classes to tick.
- **Booking first:** a ticked class the student isn't booked into is booked for them, then checked in.
- **Refusals:** any API refusal (no membership, outside the check-in window, rank gate, full) is shown as the reason.
- **Recent check-ins:** today, newest first.
- **On the tablet, names show as "Lucas M."** (Decision 351).

**What waits for you.** Each missing piece is behind one switch in `apps/school-portal/src/frontdesk/frontDeskFeatures.ts` (all `false` today). Its screen is built and shows a "Soon" state, so nothing pretends to work. The client calls you'll replace are stubbed in `apps/school-portal/src/frontdesk/kioskApi.ts`, each naming its item below. **To finish an item:**
1. Build the endpoint.
2. Replace the stub body with the `apiClient` call, after regenerating the client.
3. Turn the switch on.
4. Add a browser test next to `apps/school-portal/e2e/front-desk.spec.ts`.

## The items

### F1. Locked front-desk session `kioskSession` (Decisions 317, 320, 351; backlog §3.21)
**Today:** front-desk mode runs in the staff member's own login, with a banner saying it isn't locked. Exit only asks to confirm. **This is the most important item: an unattended tablet must not hold a staff token.**

**Needed:**
- **`POST /schools/{schoolId}/front-desk/sessions`** `{ branchId }` → `{ sessionToken, branchId, expiresAt }`.
  - Called by staff (Owner/Manager, or Branch Staff for their Branch).
  - Records who started it.
- **The kiosk token can only reach the front-desk endpoints below**, for that School and Branch. It must not carry the starter's own rights.
- **Kiosk-scoped reads** (the screen calls these instead of the staff ones once F1 is on):
  - today's classes at the Branch;
  - name search returning only `{ id, firstName, surnameInitial, profilePhotoUrl (child: only while the Guardian's camera consent is active, Decisions 57/69), kind: MEMBER | VISITOR }`;
  - recent check-ins: today only, at most 10, first name and initial (Decision 351);
  - the welcome card: membership status, waiver status (F4) and belt progress;
  - check-in (F7).
- **Rate limits** on name search and code entry, per session. Log failures.

### F2. Leave with a staff code `kioskSession` (Decision 320)
- **`POST /front-desk/sessions/{id}/unlock`** `{ staffCode }` → `{ unlockedBy }`. It ends the session and logs who unlocked it. A wrong code returns 403 with a message; rate-limit it.
- **Staff codes** are generated by ULTM8, one per staff member, with no shared School code. Staff also need a way to see and regenerate their own code (Access page, Decision 320).

### F3. Personal check-in code `personalCode` (Decision 315; backlog §3.2)
- **Each student has a code** generated by ULTM8: 4 or 6 digits by School setting (4 by default), unique in the School. Staff can issue a new one; the student can't change it.
- **`POST /front-desk/check-in-code`** `{ code }` → `{ studentId, firstName, surname, profilePhotoUrl }`. This opens the welcome card; the check-in itself is F7.
  - Add a `CheckInMethod` value such as `PERSONAL_CODE`.
  - The staff tab uses the same lookup with a staff token.
- **Rate-limit** per device and Branch.

### F4. Waiver status for one student `waiverStatus`
**Today:** no endpoint returns one student's waiver status. The card shows "Waiver status: soon".

**Needed:** `GET /students/{id}/waiver-status?schoolId=` → `{ allSigned: boolean, missing: [{ waiverId, title }] }`, open to staff at the School and to the kiosk session. A Guardian signs for a child.

### F5. Sign-up from the tablet `signUp` (Decisions 315, 318, 351)
- **`POST /schools/{schoolId}/sign-ups`** with:
  - `source: FRONT_DESK`
  - `kind` (VISITOR | MEMBER)
  - firstName, surname, dateOfBirth, gender (FEMALE | MALE | empty, Decision 315)
  - phone, email, heardFrom
  - emergency contact: name, phone, relationship
- **It creates a sign-up waiting for staff approval**, not a member (Decision 351).
- **A child can be signed up only by their Guardian**, with consent, as for any child account. The API must refuse an under-age self sign-up.
- **Staff need an approval list.** It isn't designed yet; design it with the sign-up forms of Decision 318.
- **Rejected** (Decisions 362, 365):
  - The person gets a polite email saying the sign-up wasn't accepted and to talk to the front desk. No reason is given.
  - What they typed is kept for 30 days, in a list of rejected sign-ups, then deleted.
  - Within those 30 days staff can still **approve** it: the person becomes a member straight away and gets the normal welcome email. Record who rejected it and who approved it.
  - Website sign-ups (Decision 318) follow the same rules.

### F6. Find me `findMe` (Decision 351)
- **`POST /front-desk/find-me`** returns only `{ alreadyMember: boolean }`. It never returns or fills in stored details.
- **Request:** `{ fullName, dateOfBirth }`. Both must match a member of the School (Decision 362), so nobody can find out who is a member by typing names. The screen already asks for both.

### F7. One check-in call for several classes (recommended)
**Today:** the screen loops per ticked class. For each one it calls `POST /classes/{id}/book` (if not booked), then `POST /classes/{id}/attendance-scan`. If the second class fails, the first is already done, and the card shows the error.

**Two problems:**
- **Not atomic:** a failure part-way leaves some classes done.
- **The app QR lasts about 20 s** (`QR_ATTENDANCE_TOKEN_TTL_SECONDS`). A member who takes longer to tick classes gets "The QR has expired. Ask them to show it again".

**Suggested:** `POST /front-desk/check-ins` `{ studentId | studentToken | personalCode, classIds[] }`:
- books where needed and checks in, all in one transaction, under the School's check-in rules (F9);
- returns per class `{ classId, ok, reason? }`;
- **for the QR:** verify the token when the welcome card opens (`POST /front-desk/lookup` `{ studentToken }` → a short-lived lookup id), so ticking classes isn't a race.

### F8. Pack used up: buy the same pack (Decision 316 item 7)
**Today:** the API's refusal ("no Active Membership …") is shown.

**Needed:**
- An endpoint that starts the same pack's purchase for the student, sending the payment to their app.
- A way for the card to know when the payment is done and the check-in can complete.

The design's "Pack used up" card is in DESIGN.md and on board 5b.

### F9. Check-in rules per School (Decision 317; backlog §3.5)
The screen already shows any refusal reason the API returns. When the rules exist, return their reasons in the same error shape. No frontend change is needed beyond F7's per-class reasons.

### F10. Start an open mat `openMat` (Decision 304)
The **+ Open mat session** button on the staff tab is shown switched off. It needs the Decision 304 endpoint: style, start time and length; students told in the app.

## Notes for whoever picks this up

- **The rules are decided** (Decisions 315, 317, 320, 351, 362, 365). Anything not covered there: ask the product owner before building it.
- **The tablet's privacy rules are server-side once F1 exists.** Today the staff token returns full names and the screen shortens them. With a kiosk token, the API must return only the short form.
- **Branch filter:** `GET /schools/{id}/classes` has no Branch filter, so the screen filters on `branchId`. Adding `branchId` to that query would save the client work.
- **Check-in time:** a booking's `updatedAt` is its check-in time (schema comment on Booking). A real `checkedInAt` column would make "Recent check-ins" exact.
